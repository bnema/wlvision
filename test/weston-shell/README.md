# Purpose-built Weston shell probe

Proves **Option A** of `docs/weston-baseline.md` end to end: when wlvision
ships the shell, the module that owns the `weston_desktop` instance can
enumerate, activate and resize an application toplevel using only public
libweston APIs.

The blocking finding recorded in `docs/weston-baseline.md` is that a module
loaded *beside* the normal desktop shell cannot see or control toplevels,
because `weston_desktop_surface` objects belong to a per-shell
`weston_desktop` instance and there is no reverse lookup from
`struct weston_surface`. This directory builds the smallest shell that proves
the alternative, and nothing more.

## Files

| File | Role |
| --- | --- |
| `Containerfile.inputs` | inputs stage; byte-identical to `test/weston-probe/Containerfile.inputs` and uses the same image tag, so the probe's cached input image is reused |
| `Containerfile` | verification stage; `FROM wlvision-weston-inputs:local`, builds the pinned Weston with `--network=none`, generates xdg-shell bindings, builds the shell module and both clients |
| `wlvision-shell-probe.c` | the shell module (`wlvision-shell-probe.so`, exports `wet_module_init` and `wet_shell_init`) |
| `wlvision-shell-client.c` | xdg_toplevel client with a known title/app id; waits for a configure, commits a matching shm buffer, waits for the resize configure, commits again |
| `wlvision-fixture.c` | Phase 5 fixture client (`/usr/local/bin/wlvision-fixture`); one binary whose flags select cooperative/delayed/ignored/exit/no resize handling, animation bursts, a quiet screen and input reporting |
| `run.sh` | builds both images, runs Weston headless with `shell=wlvision-shell-probe`, runs the client, asserts on the shell report, always removes the container |

Nothing is generated by hand: the xdg-shell client bindings are produced by
`wayland-scanner` from the `wayland-protocols` XML installed in the image.

## Commands

```sh
bash test/weston-shell/run.sh
```

`run.sh` runs, in order:

```sh
# 1. inputs stage - the only stage with network access (cached from the probe)
docker build -t wlvision-weston-inputs:local \
    -f test/weston-shell/Containerfile.inputs test/weston-shell

# 2. verification stage - must run with no network at all
docker build --network=none -t wlvision-weston-shell:local \
    -f test/weston-shell/Containerfile test/weston-shell

# 3. run, then assert; inside the container:
#    weston --backend=headless-backend.so --use-pixman --fake-seat \
#        --width=1024 --height=640 --socket=wlvision-test \
#        --shell=wlvision-shell-probe
#    WAYLAND_DISPLAY=wlvision-test wlvision-shell-client
#    WAYLAND_DISPLAY=wlvision-test wlvision-fixture --frames 4 --animate \
#        --period 0 --exit-after 3000
#    WAYLAND_DISPLAY=wlvision-test wlvision-fixture --frames 1 \
#        --resize ignore --exit-after 1500
#    WAYLAND_DISPLAY=wlvision-test wlvision-fixture --resize delayed \
#        --resize-delay 300 --exit-after 1500
```

`run.sh` runs the original client first, then six fixture modes against the same
Weston instance; the fixture's own stdout lines are printed between
`wlvision-inner: --- fixture NAME ---` markers and asserted per mode.

`bash -n test/weston-shell/run.sh` is clean and the file mode is 755.

## How the module is loaded (and why there are two file names)

Weston's shell loader (`frontend/main.c:wet_load_shell()`) appends
`-shell.so` to the `[core] shell=` name and looks up `wet_shell_init()` with
`dlsym()`. The required artifact name is `wlvision-shell-probe.so`, so the
image installs both names:

```
/usr/lib/weston/wlvision-shell-probe.so          <- built module
/usr/lib/weston/wlvision-shell-probe-shell.so    -> wlvision-shell-probe.so
```

`shell=wlvision-shell-probe` therefore loads the module, and the module
exports `wet_module_init` as required (both entry points run the same
init, guarded by `weston_compositor_add_destroy_listener_once()`). Verified
in the image:

```
$ ls -l /usr/lib/weston
-rwxr-xr-x wlvision-shell-probe.so
lrwxrwxrwx wlvision-shell-probe-shell.so -> wlvision-shell-probe.so
$ nm -D --defined-only /usr/lib/weston/wlvision-shell-probe.so
00000000000033a9 T wet_module_init
0000000000003387 T wet_shell_init
$ ldd /usr/lib/weston/wlvision-shell-probe.so | head -3
libweston-16.so.0 => /usr/lib/libweston-16.so.0
libwayland-server.so.0 => /usr/lib/libwayland-server.so.0
```

The client links only `libwayland-client.so.0` (plus `libm`).

Runtime flags that matter:

* `--fake-seat` (headless backend option): the headless backend only creates
  its seat - `weston_seat_init()` + pointer + keyboard - when the fake seat is
  requested. Without a seat there is nothing to give keyboard focus to.
* `--use-pixman`: the image is built without the GL renderer.
* `--width=1024 --height=640`: the headless output size (the default).

## Phase 5 fixture client (`/usr/local/bin/wlvision-fixture`)

The Phase 5 integration gates (animations, visual diffs, resize races, quiet
screens, input reporting) need a native-Wayland client they can drive
repeatably.  One binary covers all of it; flags select the behaviour.  It is
built in the last layer of the `Containerfile` from the xdg-shell bindings
generated for the original client, plus `libxkbcommon` for key reporting.

### Flags

| Flag | Default | Meaning |
| --- | --- | --- |
| `--title NAME` | `wlvision-fixture` | `xdg_toplevel.set_title` |
| `--app-id ID` | `wlvision.fixture` | `xdg_toplevel.set_app_id` |
| `--width N` `--height N` | 320x240 | size used when a configure carries no size |
| `--frames N` | 1 | frames to commit after the first map; the first map commit is frame 1 |
| `--period MS` | 40 | minimum spacing between animation commits; 0 = one commit per frame callback |
| `--animate` | off | draw a per-frame rectangle (different position *and* colour) instead of identical frames |
| `--resize MODE` | `cooperative` | `cooperative`, `delayed`, `ignore`, `exit`, `none` |
| `--resize-delay MS` | 300 | `delayed` mode wait before the matching commit |
| `--report-input` | off | bind `wl_seat` and print keyboard/pointer events |
| `--exit-after MS` | 0 (no deadline) | hard deadline; the fixture still prints `done` and exits 0 |

### Resize modes

Every mode acks every configure and the *first* configure always gets a
matching buffer, so a window exists no matter what.  On a later configure with
a different size:

| Mode | Behaviour | Why the gates need it |
| --- | --- | --- |
| `cooperative` | ack and commit a matching buffer immediately | baseline resize acknowledgement |
| `delayed` | ack, wait `--resize-delay` ms, then commit the matching buffer | race between shm buffer reuse and configure acknowledgements |
| `ignore` | ack but never commit a matching buffer; keep the old one | a client that acknowledges a resize without reallocating |
| `exit` | destroy the window immediately during the resize | toplevel destroyed while a resize is in flight |
| `none` | like `cooperative`, but never treated as settled, so the window stays up until `--exit-after` | quiet screen / stable baseline |

### Output lines

All lines go to stdout and are flushed after each one:

```
wlvision-fixture: connected
wlvision-fixture: configure n=<count> width=<w> height=<h> activated=<yes|no>
wlvision-fixture: committed width=<w> height=<h> frame=<n>
wlvision-fixture: done frames=<n> configures=<n>
```

With `--report-input`, one line per injected event:

```
wlvision-fixture: key keycode=<evdev keycode> state=<pressed|released> utf8=<text or none>
wlvision-fixture: pointer motion x=<fixed> y=<fixed>
wlvision-fixture: pointer button button=<n> state=<pressed|released>
wlvision-fixture: pointer axis axis=<n> value=<fixed>
```

The key text comes from the keymap the compositor itself sent
(`wl_keyboard.keymap` fd -> `xkb_keymap_new_from_string`, state kept by
`xkb_state_update_mask`/`xkb_state_update_key`); the pointer values are raw
`wl_fixed_t` integers, not interpreted.  A missing global, a failed connect or
a failed `mmap` is a hard failure on stderr with a non-zero exit; a normal
shutdown (including a compositor that disappears) always exits 0.

### Why the pixels are stable

Each buffer is filled with one fixed base colour.  Without `--animate` every
committed frame is byte-identical.  With `--animate` exactly one rectangle is
overdrawn at `(frame*37 % span_x, frame*23 % span_y)` in
`0xff000000 | (frame*2654435761 & 0xffffff)`, a pure function of the frame
index: no randomness and no clock enter the pixels, so two runs produce the
same digests while consecutive frames differ.

### Notes and limits

* The loop is prepared-read/poll based and driven by `wl_surface.frame`
  callbacks: it never sleeps.  The poll timeout only enforces the animation
  period, the delayed-resize deadline and `--exit-after`, so a compositor that
  stops sending frame callbacks (nothing changed) cannot stall the fixture.
* `run.sh` exercises six modes (animation burst, ignore, delayed, input, quiet,
  exit) and asserts each one's lines; `--report-input` proves the seat binding
  and the xkbcommon linkage, but the headless `--fake-seat` backend cannot
  inject key or pointer events from outside Weston, so the `key`/`pointer`
  output lines are only exercised by the Phase 5 gates that can inject them.
* `--frames N` counts all commits of an animation burst: the first map commit
  plus one per frame callback until `N` is reached, which is why
  `--frames 4 --animate` reports exactly `frame=1..4` with `done frames=4`.

## What the shell can and cannot do with the public libweston API

Everything this probe sets out to do works with installed public headers and
exported symbols only. **No private header, no private function and no Weston
source patch was needed.**

| Capability | Public interface used | Result |
| --- | --- | --- |
| Enumerate added/removed toplevels | `struct weston_desktop_api.surface_added` / `.surface_removed` via `weston_desktop_create()` | works |
| Title, app id, geometry | `weston_desktop_surface_get_title`, `_get_app_id`, `_get_geometry` | works |
| Committed buffer size | `weston_surface_get_content_size()` (public; no accessor for the raw buffer needed) | works |
| Create/map a view into a layer | `weston_desktop_surface_create_view`, `weston_surface_map`, `weston_view_set_position`, `weston_view_move_to_layer`, `weston_layer_init`/`_set_position` | works |
| Activation + keyboard focus | `weston_view_activate_input(view, seat, 0)`; `weston_seat_get_keyboard`, `keyboard->focus`; `weston_desktop_surface_set_activated` | works |
| xdg activated state reaches the client | propagated by the xdg-shell role on the next configure | client saw `activated=yes` |
| Resize acknowledgement | `weston_desktop_surface_set_size(640, 480)` -> configure -> client ack + matching buffer | works |
| Multiple windows, stable non-reused handles | one `weston_desktop` instance, per-surface `user_data`, monotonic handle counter | works |

Caveats found, none of which is an API gap for Option A:

* **A shell must paint something.** `weston_output_repaint()` asserts that the
  scene graph is not empty (`libweston/compositor.c`), so a shell that only
  maps client surfaces crashes Weston at the first repaint. Workaround is
  public: `weston_shell_utils_curtain_create()` from the installed
  `libweston/shell-utils.h` (also exported) gives a solid-colour background;
  the probe puts it in a `WESTON_LAYER_POSITION_BACKGROUND` layer. Upstream
  `kiosk-shell` and the test desktop shell do the same.
* **Keyboard focus needs a seat that has a keyboard.** `weston_seat_set_keyboard_focus()`
  is private; the public entry point is `weston_view_activate_input()`, which
  calls it and emits the compositor activate signal. With the headless backend
  the seat must be requested with `--fake-seat`; a real backend provides one
  from its input devices. Not an API limitation.
* **Activation policy is shell code, not API.** The probe activates each
  toplevel once, when it first gets content, and deactivates the previously
  focused one (`weston_desktop_surface_set_activated(prev, false)`). There is
  no public "click-to-activate" helper; a real wlvision shell has to add the
  policy (click/touch bindings are public: `weston_compositor_add_button_binding`
  as in `kiosk-shell`). Not an API gap.
* **No reverse lookup from `weston_surface`.** This is the original blocking
  finding and stays true: `weston_surface_get_desktop_surface()` only works
  for surfaces the calling module's own `weston_desktop` instance created.
  That is exactly why the shell must be wlvision's, and this probe confirms
  that owning the instance removes the problem.

Not exercised by this probe (out of scope, no API blocker identified): output
configuration beyond the single headless output, interactive move/resize
(handlers are stubs), close via `weston_desktop_surface_close`, decorations,
`xdg-shell` popups/maximized/fullscreen, and surface counters/capture.

## Reproducibility notes

* `Containerfile.inputs` is byte-identical to the probe's, under the same
  image tag, so the expensive "fetch + verify + download deps" stage is reused
  from cache. It still needs the network the first time it is built.
* The verification stage never fetches: `run.sh` builds it with
  `--network=none`, and all `.pkg.tar.zst` dependencies come from
  `/opt/weston-deps`.
* `git status --short` shows this task's only new path as
  `test/weston-shell/`; `go.mod` was already modified before this work
  started and was not touched.
